# Phase 2.5: one path contract and a sync folder (design)

Phase 2.5 of the macOS launcher's plan ([zotero-launcher-macos `PLAN.md`](https://github.com/mbradaschia/zotero-launcher-macos/blob/main/PLAN.md),
revision 3, decisions 8, 12 and 13). The work is all in this repository. The Mac app picks it up
with a pin bump and starts calling it in its phase 3a.

## Why

You use the Omarchy machine and the Mac equally. Your pins, saved searches, to-dos, layout,
prompts, taxonomies, rules, chats and artifacts should be the same on both. Zotero already syncs
the library. These files live in local folders, and three programs (this launcher, the runner,
the Mac app) each hardcode where they are.

Phase 2.5 makes one place decide where every file lives, and lets you point the shared ones at a
folder you sync between the machines (Syncthing suggested; Dropbox works). The apps sync nothing
themselves.

## What it does not do

- **Merging conflict copies.** `lib/Merge.js`, tombstones and `updated` on pins and searches are
  phase 4b. Until then, a conflict copy Syncthing leaves is ignored: the file it sits next to is
  used as is.
- **The automation host rule.** `automationHost` is stored and shown in 2.5; the scheduler obeys
  it in phase 7.
- **Any Swift code.** The Mac app calls `Paths.js` from its phase 3a.

## Success

- With no sync folder set, the launcher and the runner behave exactly as today: same paths, same
  files, same bytes.
- With one set, every synced file is read from and written to it, by the launcher and by the
  runner, including a runner started by hand in a terminal.
- Joining a second machine never loses its own data: it goes to a dated backup.
- A missing sync folder never splits your data: synced files are read-only until it's back.

## 1. `lib/Paths.js`

Plain ES5 with `module.exports`, like the rest of `lib/`. No I/O: callers read and write.

```js
Paths.settingsFile(env)                       // the machine settings file, from env only
Paths.resolve(env, machineSettings, probe)    // every other path
Paths.SETTING_SCOPES                          // section 2
Paths.combineSettings(machineRaw, sharedRaw)  // section 2
Paths.splitSettings(file, syncOn)             // section 2
Paths.syncPlan(before, after, probe)          // section 3
```

**`env`** is a plain object: `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`,
`OMA_ZOTERO_PROMPTS_DIR`, and `hostname`.
- The QML builds it from `Quickshell.env` and reads `hostname` from `/etc/hostname`.
- The runner passes `process.env` plus `os.hostname()`.
- The Mac app will pass `ProcessInfo`'s environment plus its host name.

**`machineSettings`** is the parsed machine settings file, or `null`.

**`probe`** is `{ syncMarker: bool }`: whether `<syncDir>/shared/oma-zotero-sync.json` exists.
The caller checks.

### What `resolve` returns

`config` = `$XDG_CONFIG_HOME` or `~/.config`; `cdir` = `<config>/omarchy/oma-zotero-launcher`;
`state` = `($XDG_STATE_HOME or ~/.local/state)/oma-zotero`; `cache` = `($XDG_CACHE_HOME or ~/.cache)/oma-zotero-launcher`;
`shared` = `<syncDir>/shared`.

| Key | No `syncDir` (today) | With `syncDir` |
|---|---|---|
| `sharedSettings` | `null` | `<shared>/settings.json` |
| `pins` | `<cdir>/pins.json` | `<shared>/pins.json` |
| `searches` | `<cdir>/searches.json` | `<shared>/searches.json` |
| `todos` | `<cdir>/todos.json` | `<shared>/todos.json` |
| `view` | `<cdir>/view.json` | `<shared>/view.json` |
| `instructions` | `<cdir>/instructions.md` | `<shared>/instructions.md` |
| `prompts` | `$OMA_ZOTERO_PROMPTS_DIR` or `<cdir>/prompts` | `$OMA_ZOTERO_PROMPTS_DIR` or `<shared>/prompts` |
| `taxonomies` | `<cdir>/taxonomies` | `<shared>/taxonomies` |
| `taxonomyState` | `<state>/taxonomy.json` | `<shared>/taxonomy.json` |
| `chats` | `<state>/chats` | `<shared>/chats` |
| `artifacts` | `general.artifactsDir` or `<state>/artifacts` | `general.artifactsDir` or `<shared>/artifacts` |
| `extract` | `<cdir>/extract.json` | unchanged |
| `runnerTasks` | `<state>/tasks` | unchanged |
| `runnerState` | `<state>` (the CLI's state dir, the providers' working dir) | unchanged |
| `promptVersions` | `<state>/prompt-versions.json` | unchanged |
| `keyTests` | `<state>/key-tests.json` | unchanged |
| `modelsCache` | `<cache>/models.json` | unchanged |
| `providerCache` | `<cache>` | unchanged |
| `backups` | `<cdir>/sync-backups` | unchanged |

Plus:
- `syncDir`: the absolute path in use, or `null`
- `machine`: `general.machineName`, else `env.hostname`, else `"this machine"`
- `readOnly`: `true` only when sync is unavailable (below)
- `problems`: a list of codes, empty when all is well

### Rules

- `syncDir` comes from `general.syncDir` in the machine file. A leading `~/` expands to `HOME`.
  After that it must be absolute. Otherwise it's ignored, `problems` gets `"sync-dir-invalid"`, and
  every path is today's.
- **Sync unavailable:** `syncDir` is valid but `probe.syncMarker` is false. The paths still point
  into `<shared>`. (A plan in progress can't trip this: it writes `syncDir` last, so until it
  finishes the machine file still has the old value.) `readOnly` is `true`, and `problems` gets
  `"sync-unavailable"`. There is never a fallback to the local files, because that would split
  your data.
- Every returned path is a plain string, with no trailing slash.

## 2. Two settings files

### Scopes

`Paths.SETTING_SCOPES` maps every key `Settings.toFile` can write, plus the new ones, to `"machine"`
or `"shared"`:

| Scope | Keys |
|---|---|
| machine | `general.port`, `general.externalPdfCommand`, `general.promptCommand`, `general.zoteroCommand`, `general.artifactsDir`, `general.syncDir` (new), `general.machineName` (new) |
| shared | `general.enterAction`, `general.maxResults`, `general.accelerators`, `general.emptyQuery`, `general.keys`, `general.keysStart`, `general.keyDelay`, `general.citationStyle`, `general.automationHost` (new) |
| shared | the whole of `providers`, `defaults`, `tasks`, `status` and `rules` |

API keys aren't settings; they stay in each machine's secret store. A provider enabled through
the shared settings, on a machine without its key, shows in that machine's setup checklist as
today.

### The files

- **The machine file** stays where it is (`<config>/omarchy/oma-zotero-launcher.json`).
- **The shared file** is `<shared>/settings.json`.
- **Shape:** both use today's sections (`general`, `providers`, `defaults`, `tasks`, `status`,
  `rules`), each holding only its own keys.
- **With sync off**, the machine file is exactly today's file, all keys included.

### Reading and writing

- `combineSettings(machineRaw, sharedRaw)` returns one object in today's file shape:
  - machine keys from the machine file
  - shared keys from the shared file, falling back to the machine file's value where the shared
    file lacks the key
  - with `sharedRaw` null, `machineRaw` unchanged
- `splitSettings(file, syncOn)` returns `{ machine, shared }`. With `syncOn` false, `machine` is
  `file` and `shared` is `null`.
- A section or key missing from `SETTING_SCOPES` (from a newer version, or added by hand) stays
  in the machine file. Nothing is dropped, and nothing unknown travels.
- **Who uses them:**
  - `Service.qml` reads both files, combines them, and hands the result to `Client.normalizeSettings`
    as today. Saving splits and writes each file.
  - The runner's `loadSettings` reads both through `paths.mjs`, combines them, then
    `readSettings`, as today.
- **New `general` keys** in `Settings.GENERAL` and `GENERAL_DEFAULTS`: `syncDir` (null),
  `machineName` (null), `automationHost` (null).
- **The badge:** with sync on, Settings rows for machine-scoped keys show a badge, "this machine",
  so you know which values don't travel.

## 3. Turning sync on and off

Settings › General gets three rows, all edit rows: **Sync folder** (`syncDir`), **Machine name**
(empty means the hostname), and **Automation host** (a machine name; empty means none). Changing
the sync folder runs a plan; the other two are plain settings.

### The planner

`Paths.syncPlan(before, after, probe)`:
- **Inputs:**
  - `before` and `after` are `resolve` results for the old and new `syncDir`
  - `probe` is `{ syncMarker, exists: { <path>: bool } }`, with every path the plan may touch
    checked by the caller
- **Output:** `{ kind, ops, settings }`:
  - `ops`: an ordered list of `{ op: "mkdir" | "copy" | "move" | "write", from?, to, text? }`
  - `settings`: the two files' new contents

| Kind | When | Ops |
|---|---|---|
| `fill` | a `syncDir` is set, no marker (the first machine) | `mkdir <shared>`; `copy` each synced file or folder that exists locally into `<shared>`; `write <shared>/settings.json` (the shared keys); `write <syncDir>/.stignore` if absent; `write` the marker; `write` the machine file (machine keys only, with `syncDir`) |
| `join` | a `syncDir` is set, the marker exists | `mkdir <backups>/<date>`; `move` each synced local file or folder that exists into the backup; `copy` the machine file into the backup; `write` the machine file (machine keys only, with `syncDir`) |
| `leave` | `syncDir` cleared | `mkdir <backups>/<date>`; `move` each local synced item that exists into the backup; `copy` each item from `<shared>` back to its local place; `write` the machine file (the combined settings, without `syncDir`) |
| `switch` | one `syncDir` to another | `leave`'s ops, then `fill`'s or `join`'s for the new folder, as one plan |
| `none` | nothing changed | no ops |

**What counts as synced:** the keys of section 1 that change with `syncDir`, except `prompts`
when `OMA_ZOTERO_PROMPTS_DIR` is set and `artifacts` when `artifactsDir` is set. Those stay where
you put them.

**`<date>`** is `YYYY-MM-DD-HHMMSS` in local time, passed in by the caller (no clock in `Paths.js`).

**The marker**, `oma-zotero-sync.json`, is `{ "version": 1, "created": <ISO date>, "by": <machine> }`.
**`.stignore`** is `*.tmp` and `.DS_Store`, one per line.

### Running a plan

- **The QML** runs it with `scripts/sync-apply.sh`, through a `Process`, with each op as
  arguments: `mkdir DIR`, `copy FROM TO` (`cp -Rp`), `move FROM TO` (`mv`), and
  `write PATH` (stdin to a temp file, then rename).
  - It uses `set -eu`. It stops at the first failure and prints the failing op on stderr.
  - `copy` overwrites; `move` skips a missing source. Running a plan twice gives the same result.
- **`syncDir` is written last:** the machine file's new contents carry it, as the plan's last
  `write`. A plan that fails part-way leaves `syncDir` as it was. Settings shows the failing op,
  and **Retry** reruns the whole plan.
- **The runner** never runs plans. It only reads the result.

## 4. Writes

- **The runner:** `daemon/lib/atomic.mjs` exports `writeAtomic(path, text)`. It writes
  `<path>.<pid>.tmp` in the same folder, then renames it over `path`; it removes the temp file if
  the write fails. Every runner write to a path `resolve` marks as synced uses it:
  - `prompts.mjs`, `taxonomies.mjs` (taxonomies and `taxonomy.json`), `chat.mjs`, `artifacts.mjs`,
    `system.mjs` (`instructions.md`)
  - the writers already atomic (`keytests.mjs`, `libs.mjs`, `chat.mjs`) switch to it too
- **The QML:** every `FileView` that writes a synced file must replace it by rename.
  - **Plan task 1** reads the pinned Quickshell's `FileView` for its atomic-write behavior and the
    property that controls it, and sets that property explicitly on those `FileView`s.
  - **If `FileView` can't**, those writes go through `sync-apply.sh write` instead.
- **Read-only:** while `readOnly` is true:
  - `Service.qml`'s writers of synced files (`saveSearches`, `setViewPref`, the todos and pins
    writers, the shared settings save) don't write, and set the launcher's
    error line to "Sync folder not found: <path>".
  - The runner's writing commands (new prompt, edit, chat, artifact, classify, system edit) exit
    with that message and code 3.
- **The search row:** with `problems` non-empty, the empty search shows one row at the top naming
  the problem. Enter opens Settings › General.

## 5. The runner

- **`daemon/lib/paths.mjs`** is the runner's only path code:

  ```js
  import { createRequire } from "node:module";
  const require = createRequire(import.meta.url);
  let P;
  try { P = require("./shared-paths.cjs"); }     // an installed runner
  catch { P = require("../../lib/Paths.js"); }   // a checkout
  export const Paths = P;
  export function paths(env = process.env) { ... }  // reads the machine file, probes the marker, calls resolve
  ```

  `paths()` reads the machine file and checks the marker on every call. Runner commands are
  short-lived, so there's no caching.
- **Its callers:** every module that builds a user-data path today calls `paths()` instead:
  `prompts.mjs:31`, `taxonomies.mjs:22,26`, `chat.mjs:9`, `artifacts.mjs:21`, `settings.mjs:10`,
  `system.mjs:42`, `catchup.mjs:21`, `keytests.mjs:10`, `models.mjs:9`, `tasks.mjs:14`,
  `providers/index.mjs:56,101`, `bin/oma-zotero-prompt.mjs:104`. Existing env overrides keep
  working (`OMA_ZOTERO_PROMPTS_DIR`; the `o.stateDir` test hook in `makeCtx`).
- **The install:** `scripts/install-runner.sh`, after its rsync, copies `lib/Paths.js` to
  `$RUNNER_DIR/lib/shared-paths.cjs`.
- **Versions:** the runner goes from 0.2.1 to 0.2.2, so the launchers' version check offers a
  reinstall. `scripts/check-versions.sh` keeps the version files aligned. While sync is on and
  the installed runner is older than 0.2.2, Settings › General shows a warning row: that runner
  still uses the old paths.

## 6. `Service.qml`

- `import "lib/Paths.js" as Paths`.
- **New:** a `machineFile` `FileView` (the machine settings) and a `sharedSettingsFile` `FileView`.
- **`paths`:** `readonly property var paths: Paths.resolve(env, machineSettingsRaw, { syncMarker: markerSeen })`.
  - `markerSeen` comes from a `FileView` on the marker (loaded → true, load failed → false).
  - `env` is built once from `Quickshell.env` and the hostname file.
- **The bindings:** `settingsPath`, `configDir`, `pinsPath`, `searchesPath`, `viewPath`,
  `todosPath`, `tasksPath`, `extractPath` and `instructionsPath` become bindings on `paths`, so
  changing `syncDir` re-points every `FileView` without a restart. The `mkdir -p` at line 1943
  creates the directory of `paths.pins`.
- **The runner:** spawning it is unchanged; it resolves its own paths (section 5).

## 9. Your checklist (about 15 minutes)

1. Update both machines. With no sync folder, check that search, pins, a saved search, a to-do and
   a prompt run work as before.
2. On the Omarchy machine, set the sync folder to a Syncthing folder (**fill**). Check that
   `<folder>/shared/` holds your files and the marker.
3. Let Syncthing copy it to the Mac. Set the same folder there (**join**). Check that the pins and
   to-dos are the Omarchy machine's, and that `sync-backups/<date>/` holds the Mac's own.
4. Pin a paper on one machine and see it on the other within a minute.
5. Stop Syncthing on one machine and rename the folder. Check the "Sync folder not found" row;
   pinning refuses with the message. Rename it back.
6. Clear the sync folder on the Mac (**leave**). Check that its local files are the synced ones,
   and that the Omarchy machine still syncs.

## Risks

| Risk | What we do |
|---|---|
| Quickshell's `FileView` doesn't replace by rename | plan task 1 checks it first; the fallback is `sync-apply.sh write` |
| A runner installed before 0.2.2 keeps old paths after sync is on | the version check offers a reinstall; Settings › General warns while the runner is older than 0.2.2 and sync is on |
| Syncthing hasn't finished the first copy when you join on the second machine | Syncthing doesn't transfer files in order, so the marker can arrive first. Join is still safe: it deletes nothing (your local files go to the backup), and the rest arrives as Syncthing finishes. The README says to wait for "Up to Date" before joining |
| A conflict copy before phase 4b | ignored; the README says so; 4b merges them |
